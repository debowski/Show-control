# ADR 0004 — Fade 0–1 s, domyślnie 0.8 s

**Status:** przyjęta
**Data:** 2026-11-13
**Kontekst:** `docs/refactor-plan.md`, faza 0, commit 0.3

## Kontekst

Trzy źródła mówią trzy różne rzeczy o czasie fade'a:

| Źródło | Wartość |
|---|---|
| etykieta UI, wpisana na sztywno (`main.py:1280`) | `2.0s` |
| komentarz przy `setValue(8)` (`main.py:1285`) | „domyślnie 2.0s" |
| realne zachowanie (suwak = 8, `_fade_duration()` = `value/10`) | `0.8 s` |
| README (2 miejsca) | zakres `0.2–2.0 s` |

Przyczyna rozjazdu jest mechaniczna: `setValue(8)` wykonuje się **przed**
`valueChanged.connect` (`main.py:1287`), więc etykieta nigdy nie dostaje
zdarzenia i zostaje na wartości wpisanej w konstruktorze.

Czyli przez cały czas życia funkcji fade realnie trwał 0.8 s, a operator
widział 2.0 s. Nikt tego nie zgłosił — co jest informacją o tym, jak bardzo
ten parametr jest istotny.

## Decyzja

**Zakres fade'a: 0–1.0 s**, krok 0.1 s, **domyślnie 0.8 s**.

- suwak: `setRange(0, 10)`, `_fade_duration()` = `value / 10.0`
- domyślna wartość: `8` (= 0.8 s, czyli dokładnie dzisiejsze realne zachowanie)
- etykieta generowana z `valueChanged`, nigdy wpisana na sztywno
- README: oba miejsca z „0.2–2.0 s" → „0–1.0 s"
- `0` = cięcie natychmiastowe (5 kroków po 1 ms — bez specjalnego przypadku)

Logika kroków **nie wymaga zmian**: `steps = max(5, int(fade_secs * 10))`,
`interval_ms = max(1, fade_secs * 1000 / steps)`. Dla 0.8 s daje 8 kroków po
100 ms, dla 0.1 s — 5 kroków po 20 ms, dla 0 — 5 kroków po 1 ms.

## Uzasadnienie zakresu

Górna granica 2.0 s była martwa: realne maksimum to 2.0 s tylko przy suwaku
na 20, a domyślnie nigdy tam nie było. Dla wydarzenia na żywo fade dłuższy niż
sekunda przestaje być przejściem, a zaczyna być pauzą — operator, który chce
dłuższego wygaszenia, chce zwykle innego efektu (zatrzymania z ciemnością),
nie wolniejszego fade'a.

Dolna granica 0.2 s była sztucznym ograniczeniem: `0` jest sensowną wartością
(„chcę cięcie, ale z przywróceniem jasności") i działa bez dodatkowego kodu.

## Konsekwencje

**Pozytywne**

- UI przestaje kłamać w obie strony: etykieta = wartość = realny czas.
- Zakres pokrywa oba realne użycia: cięcie (0) i krótkie przejście (0.8–1.0).
- Zero zmian w logice stanu przejścia — tylko w sterowaniu.

**Negatywne**

- To **zmiana widoczna dla operatora**, więc faza 0 nie jest czysto
  behavior-preserving. Wydana jako `v0.7.2` (patch): projekt jest przed 1.0,
  nie ma zewnętrznych konsumentów API, a operator aktualizuje ręcznie —
  więc nie ma czego złamać poza własnym przyzwyczajeniem.
- Ktoś, kto miał suwak na 2.0 s, po aktualizacji dostanie 1.0 s — czyli
  i tak szybciej, niż myślał, że ma.

## Odrzucone alternatywy

**Zostawić 0.2–2.0 i tylko naprawić etykietę** — zachowuje zakres, którego
górna połowa jest nieużywana, i domyślną wartość, której nikt świadomie
nie wybrał.

**Ustawić 2.0 s, żeby dopasować do etykiety i komentarza** — wydłuża realne
przejście 2.5×, powołując się na komentarz, który nigdy nie był prawdą.
